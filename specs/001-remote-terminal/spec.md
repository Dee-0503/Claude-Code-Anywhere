# Feature Specification: Claude Code Anywhere 随行终端

**Feature Branch**: `001-remote-terminal`
**Created**: 2026-02-13
**Status**: Draft
**Input**: 远程终端产品，让用户通过 Web/桌面/手机远程操控任意设备上的 Claude Code 实例

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 远程接入与会话连续性 (Priority: P1)

作为一个主要在手机上工作的用户，我希望能在手机端或其他电脑接入已部署在云服务器或本地电脑上的 Claude Code 会话，获得完整的终端体验（终端渲染、命令输入、快捷操作），并在断线后恢复会话，不中断当前任务。

**对应需求**: FR-001(部分), FR-002, FR-003

**Why this priority**: 这是产品的核心价值主张——远程接入 + 会话不丢失。没有这个能力，产品不成立。属于 V1 MVP（Phase A+B）范围。

**Independent Test**: 在一台设备上启动 Claude Code 实例，从另一台设备的浏览器远程连接，验证终端可用、输出实时、断线可恢复。无需多实例、多客户端或通知等其他功能。

**Acceptance Scenarios**:

1. **Given** 用户在客户端中配置了目标设备的地址并完成配对认证, **When** 用户发起连接, **Then** 客户端成功连接并展示 Claude Code 的完整终端界面，包含 ANSI 颜色、代码块、TUI 元素。
2. **Given** 客户端已连接到远程 Claude Code 实例, **When** Claude Code 产生输出, **Then** 用户在良好网络下 200 毫秒内看到终端输出的实时流式展示。
3. **Given** 客户端与服务端之间的网络突然中断, **When** 服务端继续接收 Claude Code 输出, **Then** 服务端将断网期间的全部输出缓存在每实例最大 1MB 的环形缓冲区中。
4. **Given** 网络中断后客户端重新连接成功, **When** 客户端发送自身最后接收的输出位置标记, **Then** 服务端自动重放从该位置到当前的所有缓存输出，终端状态无缝衔接，用户无需手动刷新。
5. **Given** 客户端重连且缓冲区中请求的历史输出已被新数据覆盖, **When** 服务端检测到数据缺口, **Then** 服务端发送当前可用的最早数据并附带提示，告知用户部分历史输出已丢失。
6. **Given** 客户端断线并重连, **When** 恢复终端状态, **Then** 不会重复执行已完成的操作。
7. **Given** Server 首次启动并在终端打印首次配对码, **When** 第一个客户端使用该配对码完成配对, **Then** 该客户端自动成为管理员设备，拥有生成新配对码、吊销其他设备 token、转移管理权的权限。
8. **Given** 用户从远程设备首次连接, **When** 输入 6 位数字配对码完成验证, **Then** 系统签发设备令牌，后续连接自动使用令牌认证，无需再输入配对码。
9. **Given** 管理员在 WebUI 中选择一台已配对设备并执行管理权转移, **When** 转移请求发送到服务端, **Then** 管理权立即转移给目标设备，原管理员降级为普通已配对设备，目标设备在线时实时收到角色变更通知。
10. **Given** 非管理员设备尝试执行管理操作（生成配对码/吊销设备/转移管理权）, **When** 请求发送到服务端, **Then** 系统拒绝并返回"无管理权限"错误。

### User Story 2 - 弱网与断线恢复 (Priority: P1)

作为一个在移动网络环境下使用的用户，我希望在弱网、断网、App 切后台等场景下不丢失任何信息，恢复连接后能无缝继续工作。

**对应需求**: FR-017, FR-018, FR-019

**Why this priority**: 移动场景（手机/平板）是核心使用场景，弱网和断线是常态。如果连接不可靠，远程终端就无法真正可用。属于 V1 MVP（Phase A+B）范围，与 US-01 共同构成 MVP 的可靠性基座。

**Independent Test**: 在移动网络下连接远程终端，模拟弱网（限速/丢包）和断网（飞行模式），验证客户端状态机切换、输入确认、离线队列缓存、重连后输出回放和离线输入确认发送全流程。

**Acceptance Scenarios**:

1. **Given** 客户端正常连接中, **When** 心跳检测超时（网络变慢）, **Then** 客户端自动切换到弱网模式，输出降频为批量推送以减少带宽消耗，界面显示"网络不稳定"提示。
2. **Given** 客户端处于弱网模式, **When** 网络恢复正常, **Then** 客户端自动切换回正常模式，输出恢复实时流式展示。
3. **Given** 用户在任何网络状态下发送输入, **When** 输入被服务端接收, **Then** 服务端回复确认消息，客户端在界面上标记该输入已送达。
4. **Given** 用户发送输入后 3 秒内未收到确认, **When** 自动重试机制触发, **Then** 系统自动重新发送该输入；若重试仍失败则明确提示用户发送失败。
5. **Given** 客户端已重试发送同一条输入, **When** 服务端收到重复的输入（相同消息标识）, **Then** 服务端不重复入队，仅回复确认。
6. **Given** 客户端完全断网, **When** 用户继续在客户端输入命令, **Then** 输入存入客户端本地的离线队列，界面提示"已离线，消息将在重连后发送"。
7. **Given** 客户端断网后重新连接成功, **When** 客户端存在离线队列中的待发送输入, **Then** 客户端展示离线队列中的所有消息，每条消息前有勾选框（默认全选），用户确认后将勾选的消息发送到服务端队列。
8. **Given** 重连后离线队列展示给用户, **When** 用户长时间未确认, **Then** 队列保持不发送也不丢弃，等待用户主动操作。
9. **Given** 客户端处于断网状态, **When** 服务端发生关键事件（如需要授权）, **Then** 通过外部推送通知用户。
10. **Given** 客户端界面, **When** 网络状态发生变化, **Then** 界面实时展示当前连接状态（已连接/弱网/已断开），用户始终知道当前网络情况。

### User Story 3 - 通知与授权闭环 (Priority: P2)

作为一个不总在电脑前的用户，我希望在手机端及时收到任务状态通知并完成阻塞性授权，以便安全地推进任务。

**对应需求**: FR-008, FR-009

**Why this priority**: 通知和授权是 Claude Code 在无人值守场景下的核心体验。权限审批阻塞会导致任务停滞。属于 V2（Phase C+D+E）范围，需要多客户端支持作为前提。

**Independent Test**: 构造 Claude Code "需权限审批"事件，验证设备优先级通知路由、已读消偿、外部推送升级链、审批操作全端同步。需要至少两个客户端同时在线。

**Acceptance Scenarios**:

1. **Given** Claude Code 触发需通知事件（任务完成/需授权/出错/方案规划完成/等待输入/对话框选择）, **When** 有多个客户端在线, **Then** 系统按用户配置的设备优先级顺序通知，优先通知电脑端。
2. **Given** 优先设备收到通知, **When** 用户在该设备上产生交互行为（窗口获焦+未读通知/终端输入/点击推送/操作审批按钮）, **Then** 其他设备上的该通知被标记为已读并取消提醒（已读消偿）。
3. **Given** 优先设备收到通知但 30 秒内无用户交互, **When** 升级延迟超时, **Then** 系统通知下一优先级设备。
4. **Given** 所有客户端都离线, **When** 等待 2 分钟后仍无客户端上线, **Then** 系统通过手机推送通知用户（含客户端深链）；再等 3 分钟无响应则发送飞书文本消息（含深链）；权限审批事件在飞书后仍无响应时触发弹窗加急。
5. **Given** 发生权限审批事件且所有外部通知均已发出, **When** 长时间无用户响应, **Then** Claude Code 侧保持持续等待，不设超时自动拒绝。
6. **Given** 用户收到权限审批通知, **When** 用户在终端中点击 Claude Code 原生渲染的加粗加亮审批按钮, **Then** 授权结果反馈给所有已连接客户端，状态同步显示。
7. **Given** 用户收到飞书文本通知, **When** 用户点击深链, **Then** 跳转到客户端对应实例完成审批操作，结果同步到所有客户端。
8. **Given** 非权限审批类事件（如任务完成、等待输入）, **When** 通知路由到达推送层, **Then** 不再升级到飞书通知——仅在设备间路由和手机推送。

### User Story 4 - 多设备多实例管理 (Priority: P2)

作为一个在多台设备上运行 Claude Code 的用户，我希望在一个客户端中集中管理所有设备上的所有实例，以便高效切换和监控。

**对应需求**: FR-012, FR-013

**Why this priority**: 多实例管理是进阶用户的效率需求，让用户在一个界面中掌控所有 Claude Code 工作。属于 V2（Phase C+D+E）范围。

**Independent Test**: 在一台设备上同时运行多个 Claude Code 实例，从客户端列出所有实例、切换查看、远程创建新实例，验证各实例独立运行互不影响。

**Acceptance Scenarios**:

1. **Given** 用户已连接到一台设备, **When** 该设备上有多个活跃的 Claude Code 实例, **Then** 客户端列出所有实例，显示项目路径和运行状态。
2. **Given** 客户端展示多个实例, **When** 用户切换到另一个实例, **Then** 终端视图切换到目标实例，原实例继续运行不受影响。
3. **Given** 用户在客户端选择某设备, **When** 用户指定项目目录并请求创建新实例, **Then** 系统在该设备上启动新的 Claude Code 实例，客户端自动切换到新实例。
4. **Given** 用户尝试在不存在的目录中创建实例, **When** 创建请求发送到服务端, **Then** 服务端返回明确错误信息，不需要回滚机制。
5. **Given** 已认证连接的用户, **When** 请求创建实例, **Then** 不需要额外权限验证——已配对设备即有权创建。

### User Story 5 - 多端输入协同 (Priority: P2)

作为一个在多个设备上同时查看同一 Claude Code 实例的用户，我希望多端输入有序协调，不会因为并发输入导致混乱。

**对应需求**: FR-004, FR-016

**Why this priority**: 多端同屏查看是远程终端的自然延伸，输入仲裁保证了多端协同的可用性。不设主控权机制，所有输入通过队列公平排序。属于 V2（Phase C+D+E）范围。

**Independent Test**: 从两台设备同时连接同一实例，分别发送输入，验证输出同步广播、输入按队列排序执行、队列全端可见可取消。

**Acceptance Scenarios**:

1. **Given** 多台设备同时连接同一 Claude Code 实例, **When** Claude Code 产生输出, **Then** 所有设备实时同步看到完全一致的终端输出。
2. **Given** 多台设备对同一实例发送输入, **When** 输入到达服务端, **Then** 所有输入按先进先出（FIFO）顺序入队，不区分设备优先级，所有设备平等。
3. **Given** Claude Code 实例处于空闲状态且队列中有待处理输入, **When** 队列头部的输入被取出, **Then** 该输入被注入终端执行，所有设备看到执行过程。
4. **Given** 输入队列中有多条消息, **When** 用户在任一设备上查看队列, **Then** 可以看到完整的队列内容，包括每条输入的来源设备名称。
5. **Given** 队列中有等待执行的消息, **When** 用户在任一设备上取消某条消息, **Then** 该消息从队列中移除，所有设备的队列视图同步更新。
6. **Given** 用户需要紧急中断当前执行, **When** 用户在任何设备上发送中断命令（如 Ctrl+C）, **Then** 中断信号立即送达终端，不经过队列排队。

### User Story 6 - 移动端命令与输入优化 (Priority: P3)

作为一个移动端用户，我希望在手机端支持原生命令与输入增强能力，以便高效完成日常操作。

**对应需求**: FR-005, FR-006, FR-007

**Why this priority**: 移动端输入优化是体验增强，Web 终端已经可以基本操作。原生 App 的快捷键栏和手势操作让移动端体验从"能用"提升到"好用"。属于 V3（Phase F+G+H）范围。

**Independent Test**: 在手机原生 App 中连接远程终端，验证软键盘修饰键栏（Ctrl/Shift/Alt/Tab/Esc/方向键）功能正确、Claude Code /命令可用、手势操作生效、横竖屏切换流畅。

**Acceptance Scenarios**:

1. **Given** 用户在手机端打开终端, **When** 需要发送修饰键组合（如 Ctrl+C、Shift+Tab）, **Then** 通过软键盘修饰键栏操作：单击修饰键进入"已按下"状态，再按目标键发送组合键，修饰键自动取消。
2. **Given** 用户双击某个修饰键, **When** 进入锁定模式, **Then** 后续所有按键都带该修饰键（类似 Caps Lock），再次点击解除锁定。
3. **Given** 用户在手机端终端中, **When** 输入 Claude Code 的 /命令（/help、/model、/resume、/exit）, **Then** 命令行为与桌面终端完全一致。
4. **Given** 用户在终端中, **When** 按方向键上/下, **Then** 可翻阅命令历史，行为与桌面终端一致。
5. **Given** 用户在手机端竖屏模式, **When** 左滑终端区域, **Then** 发送 Ctrl+C 中断信号。
6. **Given** 用户在终端中, **When** 长按终端文本区域, **Then** 进入文本选择模式，可复制选中内容。
7. **Given** 用户在手机端, **When** 双指捏合/张开, **Then** 终端字号相应缩小/放大，方便查看细节。
8. **Given** 用户将手机横置, **When** 屏幕方向切换为横屏, **Then** 终端布局自动适配为更宽的横屏模式。

### User Story 7 - 跨端显示一致性 (Priority: P3)

作为一个跨设备工作的用户，我希望手机端与桌面端在输出显示上保持一致，以便降低理解成本和误操作风险。

**对应需求**: FR-010, FR-011

**Why this priority**: 跨端显示一致性依赖终端渲染引擎的统一和固定列宽策略，是体验打磨层面的需求。基础渲染在 V1 已可用，V3 的原生客户端才需要更精细的适配。属于 V3（Phase F+G+H）范围。

**Independent Test**: 同时在桌面浏览器和手机 App 打开同一实例，对比 ANSI 颜色、代码块、表格、进度条等 TUI 元素是否一致。在手机端测试长输出的滚动和搜索功能。

**Acceptance Scenarios**:

1. **Given** Claude Code 输出包含 ANSI 颜色、代码块、表格, **When** 用户在不同客户端（Web/桌面/手机）查看, **Then** 所有客户端显示完全一致的渲染效果，无信息丢失。
2. **Given** 终端使用固定列数（默认 120 列）, **When** 用户在手机竖屏（约 45 字符宽度）查看, **Then** 终端通过缩放适配屏幕宽度，格式完整保持，用户可双指放大查看细节。
3. **Given** Claude Code 输出了大量内容, **When** 用户需要查找特定内容, **Then** 可使用终端内搜索功能快速定位，搜索响应及时。
4. **Given** 终端正在输出大量内容, **When** 用户进行滚动浏览, **Then** 滚动流畅，不阻塞新输出的显示和用户交互。
5. **Given** Claude Code 使用 Plan 模式输出方案, **When** 用户在移动端查看, **Then** Plan 模式的 TUI 布局（状态栏、模式指示器）正确渲染，与桌面端一致。

### User Story 8 - Agent Team 协作可视化 (Priority: P3)

作为一个使用 Claude Code Agent Team 功能的用户，我希望在客户端中同时看到 Lead 和所有 Teammate 的终端输出，并能独立与任何 Teammate 交互，以便高效管理团队协作。

**对应需求**: FR-014, FR-015, FR-020

**Why this priority**: Agent Team 是 Claude Code 的高级功能，使用频率低于基础远程终端但价值很高。需要多实例管理和通知体系作为基础。属于 V3（Phase F+G+H）范围。

**Independent Test**: 启动使用 Agent Team 的 Claude Code 实例，验证客户端自动检测 Teammate 创建/退出、布局自动调整、各 Teammate 可独立输入。

**Acceptance Scenarios**:

1. **Given** Claude Code 启动了 Agent Team 模式, **When** 系统通过 Hook 事件检测到 Teammate 创建, **Then** 客户端自动创建新窗格，展示该 Teammate 的终端输出。
2. **Given** 桌面端/横屏模式下有多个 Teammate, **When** 查看 Agent Team, **Then** 多窗格并排显示，每个 Teammate 一个独立窗格。
3. **Given** 手机端竖屏模式下有多个 Teammate, **When** 查看 Agent Team, **Then** 底部显示 Tab 栏，用颜色区分各 Teammate 状态（运行中/空闲/等待），点击切换全屏查看。
4. **Given** 某个 Teammate 的窗格处于活跃状态, **When** 用户向该 Teammate 输入, **Then** 输入进入该 Teammate 的独立队列，不影响其他 Teammate。
5. **Given** 一个 Teammate 完成任务并退出, **When** 系统通过 Hook 事件检测到 Teammate 退出, **Then** 客户端自动移除该窗格，重新调整布局，不影响其他 Teammate。
6. **Given** 用户收到推送通知并点击, **When** 通知关联到特定实例, **Then** App 被唤醒并直接进入对应实例的终端视图。

### Edge Cases

- **缓冲区溢出**: 客户端长时间离线导致环形缓冲区中旧数据被覆盖时，系统发送数据缺口提示并从当前可用的最早数据开始重放，而非静默丢失。
- **配对码过期**: 用户输入已过期的配对码时，系统返回明确的"配对码已过期"错误，引导用户获取新配对码。
- **设备令牌吊销**: 管理设备吊销某个已配对设备的令牌后，该设备下次连接时收到认证失败，自动跳转到配对码输入界面。
- **无头服务器配对**: 无显示器的服务器首次启动 Server 时，配对码输出到终端（通过 SSH 可见）。首个配对者成为管理员，后续设备由管理员在 WebUI 中生成新配对码。
- **管理权转移**: 管理员单向指定目标已配对设备即可完成转移，无需目标设备确认。转移立即生效：原管理员降级为普通已配对设备（保留连接但失去管理权限）；目标设备在线时实时收到角色变更通知，离线时下次连接自动获得管理权。转移过程中网络中断则转移不生效（原子操作）。非管理员发起转移请求时，系统返回"无管理权限"错误。
- **管理员丢失恢复**: 唯一管理员的 token 丢失（设备遗失、浏览器清缓存等）时，用户需通过 SSH 或物理访问 Server 终端执行 `claude-anywhere admin reset` 命令。该命令清除当前管理员状态，打印新的首次配对码，首个使用该码配对的客户端成为新管理员。此操作需要 Server 终端访问权限，保证安全性。
- **Server 重启**: 管理员状态和已配对设备信息持久化存储在 SQLite 中，Server 重启后自动恢复，已配对设备无需重新配对。重启前未过期的配对码在重启后失效，不自动生成新配对码（管理员可在 WebUI 中按需生成）。仅当数据库中无管理员记录时（首次启动或 admin reset 后），Server 才在终端打印首次配对码。
- **配对码竞态**: 每个配对码为一次性凭证，仅允许一台设备使用，由数据库事务保证原子性。第二个使用同一配对码的设备收到"配对码已使用"错误。管理员需为每台新设备分别生成独立配对码。
- **V3 Hub 管理员模型**: V3 引入 Hub 后，Hub 管理员即全局管理员，Agent（原独立 Server）接入 Hub 后不再有独立管理员概念。所有管理操作（配对码生成、设备吊销、实例管理）通过 Hub 统一完成。Agent 仅保留 V1/V2 的独立模式作为未接入 Hub 时的回退。
- **所有客户端同时断线**: 所有客户端离线时，服务端持续缓冲输出；关键事件通过外部推送通知兜底。
- **队列中消息的上下文失效**: 断网期间 Claude Code 可能已改变上下文，重连后离线队列需用户二次确认，不自动发送。
- **Ctrl+C 与队列的关系**: 中断信号不经过队列排队，任何设备可立即发送，但队列中的后续消息仍保留待处理。
- **Agent Team Hook 事件与 Plan 子代理的区分**: Agent Team Teammate 检测通过 SubagentStart/SubagentStop Hook 事件实现，需通过 agent_type 字段区分 Agent Team Teammate 和 Plan 内置子代理。
- **多修饰键叠加**: 移动端软键盘修饰键支持多键叠加（如 Ctrl+Shift），按完目标键后所有修饰键自动取消。
- **WebSocket 加密**: 生产环境下所有通信必须使用加密连接，非加密连接应被拒绝或告警。

## Requirements *(mandatory)*

### Functional Requirements

#### 远程接入与认证（V1 MVP）

- **FR-001**: 系统 MUST 支持用户配置目标设备的连接地址并进行认证。Server 首次启动时 MUST 在终端打印首次配对码（6 位数字，有效期 10 分钟），首个完成配对的客户端自动成为管理员。管理员 MUST 可生成新配对码供其他设备配对、吊销已配对设备的 token、将管理权转移给其他已配对设备。每个 Server 同一时间只有一个管理员。V1 阶段支持单设备连接；V3 阶段扩展为 Hub 架构下的多设备统一管理（Hub 管理员即全局管理员，Agent 接入后不再有独立管理员）。
- **FR-002**: 系统 MUST 提供完整的远程终端渲染能力，包括 ANSI 颜色、代码块、表格、进度条等 TUI 元素的正确显示。良好网络下终端输出延迟 MUST 小于 200 毫秒。
- **FR-003**: 系统 MUST 支持会话断线恢复。服务端 MUST 为每个实例维护最大 1MB 的输出缓冲区；重连时 MUST 按客户端最后接收位置自动回放缺失输出；缓冲区溢出时 MUST 通知客户端数据缺口范围。
- **FR-003a**: WebSocket 协议消息 MUST 包含 server_id 和 instance_id 字段（V1 阶段为固定默认值），为 V3 Hub 架构下多服务器路由预留扩展性。

#### 多端同屏与输入协同（V2）

- **FR-004**: 系统 MUST 支持多台设备同时连接同一 Claude Code 实例并同屏查看。服务端 MUST 将终端输出一致广播给所有已连接客户端。

#### 移动端输入增强（V3）

- **FR-005**: 移动端 MUST 提供软键盘修饰键栏，包含 Ctrl、Shift、Alt、Tab、Esc、方向键及常用组合键。支持单击激活、双击锁定、多键叠加三种交互模式。
- **FR-006**: Claude Code 的所有 /命令（/help、/model、/resume、/exit 等）在远程终端中的行为 MUST 与本地桌面终端完全一致。终端快捷键（Ctrl+C 中断、Ctrl+B tmux 前缀等）MUST 正确透传到远程 PTY；tmux 组合键（Ctrl+J 换行、Ctrl+A 行首等）MUST 不被客户端 UI 层拦截。
- **FR-007**: 移动端 MUST 支持手势操作（左滑中断、长按选文、双指缩放字号）和横竖屏自适应布局切换。

#### 通知与授权（V2）

- **FR-008**: 系统 MUST 实现设备优先级通知模型。多设备在线时优先通知电脑端（用户可配置优先级排序和升级延迟）；优先设备响应后通过已读消偿取消其他设备的通知。所有客户端离线时 MUST 按"手机推送 -> 飞书消息 -> 弹窗加急"路径逐级升级。各事件类型的升级范围不同：只有权限审批事件走完整升级链（含弹窗加急），CC 侧保持持续等待不自动拒绝；非审批事件（任务完成、等待输入）仅到推送层。
- **FR-009**: 用户 MUST 可在终端中 Claude Code 原生渲染的审批提示上直接批准或拒绝（客户端对审批按钮进行加粗加亮视觉增强，不额外渲染 UI 组件）。所有客户端离线时通过飞书文本消息通知审批内容并附带客户端深链。授权结果 MUST 同步到所有已连接客户端。Claude Code 侧保持持续等待，不设超时自动拒绝。

#### 跨端显示（V3）

- **FR-010**: 所有客户端（Web/桌面/手机）对同一终端输出的渲染 MUST 完全一致。终端 MUST 使用固定列数（默认 120 列），各客户端通过视觉缩放适配屏幕宽度，不改变终端逻辑布局。不支持客户端动态调整终端尺寸。
- **FR-011**: 终端 MUST 支持长输出的快速滚动和内容搜索功能。大量输出不得阻塞用户交互。

#### 多实例管理（V2）

- **FR-012**: 客户端 MUST 按工作目录（cwd）分组展示每台设备上所有活跃的 Claude Code 实例列表，一级分组为工作目录路径，目录下展示该路径对应的所有实例及其运行状态。用户 MUST 可在实例间快速切换且不中断其他实例的运行。
- **FR-013**: 用户 MUST 可从客户端远程创建新的 Claude Code 实例。V2 阶段支持在当前连接的单台设备上创建（选择项目目录、启动实例）；V3 阶段通过 Hub 扩展为在任意已连接服务器上创建和管理实例（启动/停止/删除）。已认证连接即有权创建，不做目录白名单限制。创建失败返回错误信息。

#### Agent Team（V3）

- **FR-014**: 系统 MUST 通过 Hook 事件（SubagentStart/SubagentStop/TeammateIdle）自动检测 Agent Team 的 Teammate 创建、退出和状态变化，并自动调整客户端布局。桌面端/横屏模式采用并排分窗格显示；手机端竖屏模式采用底部 Tab 栏切换，用颜色区分 Teammate 状态。
- **FR-015**: 每个 Teammate 窗格 MUST 可独立接受用户输入，输入进入该 Teammate 的独立队列。

#### 输入仲裁（V2）

- **FR-016**: 多设备对同一实例的输入 MUST 按先进先出（FIFO）队列排序。所有设备平等入队，不设主控权机制。队列 MUST 对所有已连接客户端可见，显示每条输入的来源设备名称。队列中的消息 MUST 可在任一设备上取消。中断信号（如 Ctrl+C）MUST 不经过队列，任何设备可立即发送。

#### 连接可靠性（V1 MVP / V2）

- **FR-017**: 每条用户输入 MUST 有唯一标识和服务端确认机制。3 秒未收到确认 MUST 自动重试。服务端 MUST 按消息标识去重，相同消息不重复入队。
- **FR-018**: 客户端 MUST 在离线时将未发送的输入缓存到本地离线队列。重连后 MUST 展示离线队列内容（勾选框，默认全选），由用户确认后发送。超时不确认则保持队列不丢弃。
- **FR-019**: 客户端 MUST 实现连接状态机，区分已连接、弱网、已断开三种状态，并在界面上实时展示当前状态。弱网模式下输出 MUST 降频为批量推送。重连 MUST 采用递增退避策略（从 1 秒起，最大 30 秒）。

#### 推送深链（V3）

- **FR-020**: 用户点击手机推送通知 MUST 可直接唤醒 App 并定位到对应的 Claude Code 实例终端视图。

### Key Entities

- **设备 (Device)**: 运行 Claude Code 实例的物理或虚拟主机。属性包括设备标识、设备名称（用户自定义别名）、连接地址、配对状态、管理权限标记、最后在线时间。
- **已配对设备 (Paired Device)**: 通过配对码认证成功的客户端设备。属性包括设备令牌哈希（服务端存储）、配对时间、是否为管理员（每个 Server 同一时间仅一个管理员）、令牌过期时间（默认永不过期）。管理员可将管理权转移给其他已配对设备。
- **配对码 (Pairing Code)**: 6 位数字一次性凭证，有效期 10 分钟。Server 首次启动时自动生成首次配对码（首个配对者成为管理员）。后续配对码由管理员通过 WebUI 或 CLI 生成。
- **实例 (Instance)**: 一个正在运行的 Claude Code 进程。属性包括实例标识、项目路径、运行状态（空闲/处理中）、所属设备、已连接客户端集合。可以是独立实例、Agent Team Lead 或 Teammate。
- **输出缓冲区 (Output Buffer)**: 每实例维护的环形缓冲区，容量 1MB。记录全局写入偏移量（单调递增），支持按客户端的最后接收偏移量重放缺失输出。
- **输入队列 (Input Queue)**: 每实例维护的先进先出队列。每条输入包含唯一标识、文本内容、来源客户端标识、来源设备名称、时间戳、状态（排队中/已注入/已取消）。
- **客户端连接 (Client Connection)**: 一个客户端到服务端的活跃连接。属性包括客户端标识、设备名称、连接状态（已连接/弱网/已断开）、各实例的最后接收偏移量、离线队列、推送令牌。
- **通知事件 (Notification Event)**: 需要通知用户的事件。属性包括事件类型（权限审批/方案审核/任务完成/执行出错/等待输入/对话框选择）、关联实例、详情。不同事件类型有不同的升级范围。
- **设备通知配置 (Device Notification Config)**: 用户的通知偏好设置。包括设备优先级排序、升级延迟（默认 30 秒）、通知模式（优先模式/全部同时）、免打扰设备列表、外部推送等待时间（默认 2 分钟）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

#### 核心体验（V1 MVP）

- **SC-001**: 用户从配置设备地址到看到远程终端界面，在良好网络下 MUST 在 10 秒内完成连接。
- **SC-002**: 良好网络下终端输出从产生到用户看到 MUST 在 200 毫秒以内。
- **SC-003**: 网络中断后重新连接时，MUST 在 5 秒内（良好网络）完成输出回放并恢复终端状态，用户无需手动刷新。
- **SC-004**: 断线期间产生的终端输出，在缓冲区容量范围内（1MB）MUST 100% 不丢失。
- **SC-005**: 客户端网络状态变化后，界面状态指示器 MUST 在 3 秒内更新。

#### 认证安全

- **SC-006**: 新设备配对流程（输入地址+输入配对码）MUST 在 30 秒内完成。
- **SC-007**: 首个配对者 MUST 自动成为管理员，无需额外操作。
- **SC-008**: 管理员吊销某设备令牌后，被吊销设备的下次连接 MUST 被拒绝并引导重新配对。
- **SC-008a**: 管理权转移操作 MUST 在 2 秒内完成，目标设备在线时 MUST 在 2 秒内收到角色变更通知。

#### 输入可靠性（V1+V2）

- **SC-009**: 每条用户输入发送后 MUST 在 3 秒内收到服务端确认；未确认时 MUST 自动重试。
- **SC-010**: 重复发送的同一条输入（相同标识）MUST 不产生重复执行。
- **SC-011**: 离线期间缓存的输入，重连后 MUST 完整展示给用户确认，不自动发送也不自动丢弃。

#### 多端协同（V2）

- **SC-012**: 同一实例的终端输出 MUST 在所有已连接客户端上同步显示，延迟差异不超过 100 毫秒。
- **SC-013**: 输入队列变更 MUST 在 1 秒内同步到所有已连接客户端。
- **SC-014**: 任一设备取消队列中的消息后，所有设备 MUST 在 1 秒内看到队列更新。

#### 通知效率（V2）

- **SC-015**: 权限审批事件从触发到优先设备收到通知 MUST 在 2 秒内完成。
- **SC-016**: 用户在任一设备上响应通知后，其他设备 MUST 在 2 秒内标记该通知为已读（已读消偿）。
- **SC-017**: 所有客户端离线时，外部推送 MUST 在配置的等待时间（默认 2 分钟）后准时触发。

#### 多实例管理（V2）

- **SC-018**: Server 启动时 MUST 根据可用内存和 CPU 核心数动态计算 `maxInstances` 上限（公式：`min(availableMemoryMB / 50, cpuCores * 3)`，下限为 3）；在推荐配置（8GB RAM / 4 核）下 MUST ≥10。
- **SC-019**: 单一服务端 MUST 支持至少 5 个客户端并发连接。
- **SC-020**: 实例间切换 MUST 在 500 毫秒内完成终端视图切换。

#### 移动端体验（V3）

- **SC-021**: 移动端软键盘修饰键栏发送组合键 MUST 功能正确，与桌面终端行为一致。
- **SC-022**: 横竖屏切换后终端布局 MUST 在 500 毫秒内完成自适应调整。
- **SC-023**: 终端内搜索在 1 万行输出范围内 MUST 即时响应。

#### Agent Team（V3）

- **SC-024**: Teammate 创建/退出时，客户端布局 MUST 在 2 秒内自动调整。
- **SC-025**: 各 Teammate 的输入队列 MUST 相互独立，互不干扰。

#### 质量基线

- **SC-026**: 核心模块（消息队列、输出缓冲区、输入仲裁、配对认证）的单元测试覆盖率 MUST 不低于 80%。
- **SC-027**: 客户端心跳周期 MUST 为 15 秒，服务端 MUST 在 45 秒未收到心跳后将客户端标记为离线。
- **SC-028**: 重连退避策略 MUST 从 1 秒起递增（1s、2s、4s、8s、16s），最大间隔不超过 30 秒。

## Clarifications

### Session 2026-02-13

- Q: 管理权转移是什么操作模型？（双方确认 / 单向即时 / 单向+超时回滚） → A: **单向即时**。管理员直接指定目标已配对设备，转移立即生效。目标在线时实时通知，离线时下次连接自动获得管理权。
- Q: 管理员设备永久丢失如何恢复管理权？ → A: **CLI 手动重置**。用户通过 SSH/物理访问 Server 终端执行 `claude-anywhere admin reset`，清除管理员状态并打印新首次配对码。
- Q: Server 重启后配对码与管理员状态如何处理？ → A: **管理员持久化，配对码不重新生成**。管理员状态存 SQLite，重启后保留。旧配对码重启后失效，仅首次启动或 admin reset 后才打印首次配对码。
- Q: 多客户端同时配对的竞态如何处理？ → A: **先到先得 + 配对码一次性**。同一配对码只能被一台设备使用，数据库事务保证原子性。第二个使用者收到"配对码已使用"错误。
- Q: V3 Hub 架构下管理员是分层还是统一？ → A: **统一管理员**。Hub 管理员即全局管理员，Agent 接入 Hub 后不再有独立管理员，所有管理操作通过 Hub 统一完成。
